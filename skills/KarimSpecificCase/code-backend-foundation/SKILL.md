# Code Backend Foundation

Architecture and implementation skill for the most important transition in a project's lifecycle: moving from a working frontend demo to a grounded, backend-capable system.

This skill governs the transformation of a prototype with fake data, no auth, and no persistence into a system with:
- real authentication and user identity (operator roles: trader, dispatcher, ops manager, read-only)
- database-backed persistence (user layouts, saved alerts, cavern configurations, nomination drafts)
- typed API boundaries between frontend and backend
- a real-time transport layer (SCADA ticks, market prices, alert events)
- clean separation between what is live, what is persisted, and what is derived

## Relationship to `/code-artisan`

This skill is a specialization, not a replacement. When touching UI code, DOM structure, CSS, or frontend logic during implementation, follow the standards defined in `/code-artisan`. That skill governs code quality. This skill governs the system transformation.

Do not duplicate implementation craft guidance here. Import it by reference.

---

## Why this transition matters

A prototype has a structural lie at its core: it looks like a real system but is built on fake state. Every user action that should persist does not. Every "live" value is generated by a seeded RNG. The gap between the demo and the real tool is not a matter of adding features — it requires replacing the structural foundation.

For a gas-storage dashboard the stakes are concrete. The operator needs to trust the cavern inventory number because a nomination depends on it. They need to trust the injection rate because a flow alarm depends on it. They need to trust the price curve because a hedging decision depends on it. Half-measures — a login that sets `isLoggedIn = true`, a WebSocket that pushes `Math.random() * 1000`, a localStorage "database" of cavern configurations — create the appearance of progress while making the actual transition harder. This skill is designed to prevent that.

---

## The three-state principle

This is the single most important architectural constraint. Before writing a line of implementation code, map every piece of state in the system to one of these three categories:

**1. Live operational / market state** — ephemeral data from a streaming source. SCADA ticks (cavern pressure, temperature, flow rates), price feeds, system health events, incoming alerts. This state is *received*, not *fetched*. It is not persisted by the dashboard — you consume it and it passes through. Persisting it is a separate pipeline concern (historian / time-series DB / data lake), not a UI concern.

**2. Persisted user / application state** — database-backed state that belongs to a user or to the configuration of the installation and survives sessions. Saved pane layouts, alert thresholds, watchlists, cavern metadata, nomination drafts, user preferences, operator permissions. This state must be read from and written to a real store. It cannot live in `useState` / closures alone, and it must not be conflated with live operational state.

**3. Derived or view UI state** — transient state computed from categories 1 and 2. Filter selections, sort order, currently selected cavern, hover state, expanded/collapsed panels, zoom/pan window on a chart. This lives in component / factory state or the URL. It does not need to be persisted (unless the user explicitly saves a "view configuration"), and it does not come from the server.

Mixing these three causes almost every architectural problem in demo-to-real transitions. The key symptom: a pane that subscribes to a WebSocket and also reads from localStorage and also derives a computed value from an in-memory variable, with no clear mental model of which is which.

Read `references/state_separation.md` for detailed guidance on where each type lives and how they interact.

## Execution phases

Every backend foundation task follows these phases in order. Do not compress them.

### Phase 1 — Repository audit

Read the project before proposing anything.

Produce a written audit covering:
- **Fake-data entry points** — where is fake data generated? Seeded RNG, `Math.random()`, hardcoded arrays, mock JSON blobs. These are the replacement targets.
- **Implied domain entities** — what does the UI already model? Caverns, tanks, nominations, schedules, flow events, alerts, prices, curves, users, roles? These are your schema seeds.
- **Current state model** — where does state live? Closures? A top-level `state` object? `localStorage` under `karim.*`? Identify what is local UI state, what should be persisted, and what should be streamed.
- **User flows and routing** — what does the user navigate? Which screens require authentication to be meaningful? Which state should be user-scoped vs. installation-scoped?
- **Existing backend scaffolding** — is there any? An existing API, a partial schema, half-done auth wiring? Identify what to build on vs. what to replace.
- **Conflation points** — where are backend concerns baked into the UI? A factory that constructs a data shape that should come from the API, or applies business rules that belong in the domain layer.

Do not skip this step. The audit determines the correct sequence of implementation phases and prevents building a backend layer that is incompatible with the frontend's assumptions.

### Phase 2 — Target architecture

Produce an architecture proposal before writing any implementation.

The proposal must define:
- **Auth boundary** — how users (operators, dispatchers, traders, read-only observers) are authenticated, what the session/token model is, which routes are protected, how the frontend carries identity to the backend. Role-based access where warranted (e.g., only a dispatcher can draft a nomination).
- **Database model** — which entities exist, how they are related, which are user-scoped, which are installation-scoped, which are shared. A rough schema is enough at this stage — not a full migration file. Typical entities for this project: `user`, `cavern`, `cavern_metadata`, `alert_rule`, `alert_event`, `saved_layout`, `nomination_draft`, `audit_event`.
- **API surface** — what endpoints or RPC methods the frontend calls for CRUD on persisted state. REST or tRPC or GraphQL — choose one and be consistent.
- **Real-time transport** — what events flow over WebSocket or SSE, what the message schema looks like, how the frontend subscribes and handles updates. Typical channels: `scada.tick`, `market.price`, `alert.fired`, `nomination.updated`.
- **Frontend state integration** — how the three state types wire together. Which subscribers handle live data, which handle persisted data, which handle UI state.
- **User/installation-specific persistence** — what objects are user-owned, what are installation-owned, what their schema looks like, whether lightweight versioning (e.g., layout history) is warranted.

Present this to the user before implementation. Architecture disagreements are cheap to resolve in a document; they are expensive to resolve after a DB migration.

See `references/state_separation.md`, `references/auth_patterns.md`, `references/persistence_schema_guidelines.md`, `references/realtime_transport_architecture.md`.

### Phase 3 — Staged implementation plan

Break the transformation into a sequence of phases, each of which leaves the system in a coherent runnable state.

A typical sequence for a gas-storage dashboard:

| Phase | What happens |
|---|---|
| Auth foundation | User model + roles (trader / dispatcher / ops / read-only), sign-in/out, session/token layer, protected routes |
| Schema + migrations | Database schema for cavern/alert/layout/nomination entities, migration tooling |
| API layer | Backend routes for persisted state CRUD — layouts, alert rules, cavern config, nomination drafts |
| Persistence wiring | Frontend layer that reads/writes through the API instead of `localStorage` or fake arrays |
| Real-time transport | WebSocket/SSE server, event model (`scada.tick`, `market.price`, `alert.fired`), frontend subscription layer |
| SCADA adapter | Typed adapter between the transport and the fake-data generator; real SCADA feed drops in behind the same contract |
| Market feed adapter | Same pattern: typed adapter consuming ICE / EEX / internal curve service |
| Alert engine | Server-side rule evaluation, event fan-out, acknowledgement round-trip |
| Nomination workflow | Draft → review → submit round-trip, audit log, role-based gating |
| Finalization | Audit, cleanup, handoff documentation |

The sequence is not rigid — adapt it to what the project needs. But each phase must end with the system running correctly, not just "the migration is in progress."

See `references/migration_from_demo_to_real.md` for migration patterns and adapter strategies.

### Phase 4 — Implementation

Execute the staged plan. For each phase:
- Implement one logical unit at a time.
- Replace fake data structures progressively, not all at once.
- Use **adapter patterns** to isolate the fake-to-real transition boundary — the UI should not need to change when the data source changes, only the subscription / service layer.
- Keep the frontend runnable at each step. A broken dashboard during a backend migration is a morale and debugging liability.
- Follow `/code-artisan` implementation standards for all code written.

Specific implementation guidance is in the reference documents:
- Auth: `references/auth_patterns.md`
- Schema and persistence: `references/persistence_schema_guidelines.md`
- Real-time: `references/realtime_transport_architecture.md`
- State integration: `references/state_separation.md`

### Phase 5 — Finalization

Produce a handoff summary covering:
1. **What changed** — what was fake and is now real
2. **What is still pending** — what remains mocked (e.g., real SCADA credentials not yet provisioned), what needs vendor access, what is intentionally deferred
3. **How to run the system** — environment setup, env vars, dev server commands, database setup steps, migration commands
4. **System structure** — a brief map of what lives where (backend routes, schema location, transport layer, frontend hooks/subscriptions)
5. **Extension points** — how to add a new persisted entity, how to add a new real-time event type, how to extend the auth model, how to add a new alert rule type

This summary is the difference between a completed backend foundation and a completed backend foundation that the next engineer can work with.

## Auth requirements

See `references/auth_patterns.md` for detailed patterns.

The minimum viable auth implementation:
- Real user identity (not simulated)
- Role model suited to the domain: at minimum **trader**, **dispatcher**, **ops**, **read-only**
- Sign in, sign out, session or token with a defined lifecycle
- Protected routes that redirect unauthenticated users
- Backend routes that reject unauthenticated requests, and authorize per-role where warranted (nominations, alert rule edits, cavern config edits)
- User ID + role propagated to all persisted state and audit events

Do not:
- Use `localStorage` as a session store
- Hardcode test credentials and call that "auth"
- Leave unprotected routes that should require authentication
- Conflate "user is logged in" (UI state) with "request is authenticated" (backend state)

## Persistence requirements

See `references/persistence_schema_guidelines.md` for schema patterns.

The minimum viable persistence layer:
- A real database (relational preferred for structured domain entities — caverns, nominations, alert rules)
- A migration system (so the schema is versioned and reproducible across dev / staging / prod)
- User-scoped entities with proper foreign keys (saved layouts, personal watchlists, personal alert rules)
- Installation-scoped entities (cavern metadata, shared alert rules) with clear ownership
- An **audit table** for any state change with operational consequence — nomination edits, alert acknowledgements, role changes
- An API layer that mediates all access — no direct DB access from the frontend

Do not:
- Use `localStorage` as the persistence layer for domain entities (layouts are fine; cavern config and nominations are not)
- Dump everything into a single JSON blob per user unless the entity genuinely has schemaless structure
- Skip migrations and rely on "just recreate the DB" during development

## Real-time transport requirements

See `references/realtime_transport_architecture.md` for architecture patterns.

The minimum viable real-time layer:
- A **defined event schema**, versioned — e.g., `{ "type": "scada.tick", "cavern_id": "...", "pressure_bar": ..., "ts": "..." }`. Not raw JSON blobs.
- A server-side transport (WebSocket or SSE). Prefer SSE for one-way broadcast (ticks, alerts); WebSocket when the frontend needs to publish back (subscribe/unsubscribe messages, acknowledgements).
- A client-side subscription layer that is separate from UI factories — the factory renders, the subscription layer pushes updates to the state object the factory reads.
- A clear **adapter boundary** between the transport and the shapes the UI consumes. The fake data generator and the real SCADA feed must produce the same output shape from the UI's perspective.

Do not:
- Create a WebSocket server that streams `Math.random()` and call it "live data integration"
- Inline WebSocket logic in UI factories
- Use a single catch-all message type for all events

If real vendor credentials or SCADA access are not yet available, create an adapter boundary with a typed stub. The stub should produce realistic, schema-valid data — with physically plausible ranges for pressure / temperature / flow — not random noise. This makes the real integration a one-file swap.

## HTML-lint gate (mandatory before every UI commit)

Any commit touching `index.html`, `monitor.html`, or files under `assets/` is blocked by the `html_lint_gate.py` pre-commit hook unless the file parses cleanly and contains no leaked secrets or stray `debugger;`. This applies even when the backend work is the primary change — if a migration or API wiring accidentally breaks the frontend HTML, the gate catches it.

Run manually:
```bash
python3 .claude/hooks/html_lint_gate.py < /dev/null
```

If a check fails, fix the code. The only valid edit to the gate itself is to *tighten* it (add a new check), not to loosen it.

## Anti-goals

This skill actively resists these common failure modes:

- **Fake auth** — a login form that sets `isLoggedIn: true` in JS state and routes accordingly. This is not auth.
- **localStorage as database** — workable for UI preferences (layouts, view state), not for domain entities that must be server-authoritative (nominations, alert rules, cavern config).
- **Random-number WebSocket** — a streaming endpoint that pushes `Math.random() * 100` every 500ms is not a real-time architecture.
- **Monolithic backend** — a single 2000-line `server.js` / `main.py` with all routes, all business logic, and no boundaries is not an API layer.
- **Backend logic in the frontend** — a factory that constructs raw SQL or makes direct fetch calls to external data vendors is the wrong layer.
- **Demo preservation** — if the correct move is a meaningful refactor of the demo architecture, make the refactor. Do not bolt real infrastructure onto a fundamentally fake structural foundation.
- **Enterprise overengineering** — this skill produces a *foundation*, not a service-mesh diagram. A clean Node/Express or FastAPI + Postgres + WebSocket stack is a correct answer. A 12-service microservices mesh is not.
