# Commit Quality Rubric

A commit's quality is measured against two things: the message itself, and the relationship between the message and the diff.

## Quality grades

| Grade | Definition |
|---|---|
| **Excellent** | Subject is specific and informative. If the change deserves a body, the body explains *why* and *what* without being verbose. Style is consistent with the repo. The message accurately describes the diff. |
| **Good** | Subject is specific. A body would help but its absence is not fatal. The message accurately describes the diff. |
| **Acceptable** | Subject conveys the change at a coarse level (e.g. "Refactor user model"). A reader can understand roughly what happened, but not why or what was preserved. No body where one would help. |
| **Weak** | Subject is generic, telegraphic, or partially mismatched with the diff (e.g. "Update user code" for a change that adds three new fields and a migration). Significant context is missing. |
| **Poor** | Subject is uninformative ("fix", "wip", "update"), or actively misleading. The diff cannot be summarised from the message alone. |

## Issue tags

Apply zero or more issue tags to each commit. The tags are not exclusive.

- **vague** — subject is one or two generic words, or a single placeholder (`fix`, `update`, `changes`, `wip`, `final`, `stuff`, `bugfix`, `minor changes`, `tweaks`, `more work`, `idk`).
- **too_broad** — subject covers a large diff with a single sweeping verb (`refactor everything`, `cleanup`, `improvements`).
- **too_narrow** — subject is so specific to one tiny part that the rest of the diff is invisible (e.g. message says "Rename `x` to `y`" but the commit also restructures three modules).
- **mixed_concerns** — single commit blends unrelated changes (feature + unrelated bug fix; refactor + new feature; whitespace cleanup + behaviour change).
- **missing_rationale** — non-trivial behaviour change with no explanation of why.
- **mismatch_with_diff** — message is contradicted by the actual diff (e.g. "Remove logging" but the commit *adds* logging).
- **inconsistent_style** — repo uses Conventional Commits everywhere else, this commit doesn't (or vice versa); imperative vs past tense mixing.
- **redundant** — message restates the diff at the file/function level instead of the change level (`Edit user.py`).
- **autogenerated** — message looks generated by tooling (`auto:`, `[bot]`, GUI defaults) and adds no human signal.

## Sizing heuristics

A commit is **too large** if any of the following hold:

- Touches files in more than ~3 unrelated top-level directories.
- Has more than ~500 lines changed *and* the message is a single short subject.
- Combines a refactor (mass renames, restructure) with new behaviour.

A commit is **too small** if it does literally nothing useful on its own (e.g. `fixup!` commits never squashed, or single-character whitespace changes that should have been part of an adjacent commit).

These are heuristics, not laws. A 5,000-line commit that says "Vendor `<library>` v2.4.1" is fine — the diff is mechanical. A 20-line commit that says "fix" is not fine — the diff is small but the message tells the reader nothing.

## Mismatch detection

Compare the subject against the file list and the diff:

- If the subject names a module/file (`Refactor auth.py`) and the diff touches files outside that module, flag `mismatch_with_diff`.
- If the subject describes a verb (`Add`, `Remove`, `Rename`) that contradicts the diff (e.g. `Remove unused helper` but the file is added, not removed), flag `mismatch_with_diff` and propose a corrected message in stage 4.
- If the subject is a question (`why is this here?`) or a personal note (`finally got it working`), it does not describe the change at all; flag `vague` *and* `redundant`.

## Determining "improvable"

A commit is `improvable` if **any** of:

- it has the `vague`, `too_broad`, `mixed_concerns`, `mismatch_with_diff`, or `redundant` tag,
- its quality grade is `Weak` or `Poor`,
- the diff is non-trivial (> ~30 lines or > 3 files) and the message is title-only with no body explaining the change.

A commit is **not** improvable when:

- the diff is trivial (single-character, single-line) and the message is correspondingly short but accurate,
- the message is already `Good` or `Excellent`.
