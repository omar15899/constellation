# Task Marshal — The Task Ledger

Use the [common Constellation entry](../../../README.md) for scope, evidence,
independent review and publication. Resolve consultations directly; open a scoped
assignment before a change. Domain names below identify skills or responsibilities;
use the native agent catalogue for delegation, inherit the session settings, and
leave Git integration and publication to the coordinator. Project data paths are
relative to `/Users/omarkhalil/OmarOS` unless an absolute path is given.

## Overview

OmarOS tasks live as structured YAML records inside **daily bucket files**. Omar logs with natural-language prose (often messy, often multi-task per prompt); this skill extracts each task, normalises it into a fixed schema, and appends it to the right day's file. Deterministic Python scripts then aggregate across days into weekly, monthly, and yearly views — all backed by a flat `_index.json` mirror that powers reports, dashboards, and ad-hoc analysis.

Two surfaces, one truth:

- **Daily/** — human-readable, hand-editable ledger (one file per day).
- **Weekly/ Monthly/ Yearly/ + _index.json** — machine-generated; regenerated from Daily on every change.

## When this skill runs

- User logs one or several tasks (any phrasing, any language).
- User transitions a task (`close`, `cancel`, `block`, `roll over`).
- User asks for a listing/report (`qué tengo esta semana`, `P0 abiertas`, `rollup abril`).
- `/task` command invoked.
- Another skill forwards action items (e.g. `work-scribe` from a meeting).

Do **not** run for:

- Long-form reflection → `reflection-writer`.
- "Should we do X?" decisions → `decision-logger`.
- Project narrative/state → `project-reporter`.
- Raw unclassified fragment capture → `capture` / `inbox-classifier`.

## Task schema (authoritative)

Every task is a fenced block inside a Daily file:

````
```yaml task
id: 2026-04-22-001
title: Llamar a Juan
when: 2026-04-22
time_of_day: morning
duration_min: null
status: open
priority: P0
project: null
tags: [familia, llamada]
energy: null
location: null
created_at: 2026-04-22T09:14
closed_at: null
body: null
references: null
```
````

### Fields

| Field | Type | Enum / format | Default |
|-------|------|---------------|---------|
| `id` | string | `YYYY-MM-DD-NNN` (auto, deterministic) | assigned by `log_task.py` |
| `title` | string | one-line, imperative where possible | **required** |
| `when` | string\|null | ISO date `YYYY-MM-DD` | null if no date given |
| `time_of_day` | enum\|null | `morning` / `afternoon` / `evening` / `night` | null |
| `duration_min` | int\|null | minutes | null |
| `status` | enum | `open` / `done` / `cancelled` / `rolled_over` / `blocked` / `waiting` | `open` |
| `priority` | enum\|null | `P0` / `P1` / `P2` / `P3` | null (no default — only set if user said) |
| `project` | string\|null | slug matching `05_Projects/<slug>/` | null |
| `tags` | list\[string\] | free-form, ASCII snake_case | `[]` |
| `energy` | enum\|null | `low` / `medium` / `high` | null |
| `location` | enum\|null | `home` / `office` / `outside` / `travel` | null |
| `created_at` | string | ISO timestamp | now |
| `closed_at` | string\|null | ISO timestamp | null |
| `body` | string\|null | multiline markdown — long context / explanation | null |
| `references` | string\|null | multiline markdown — ChatGPT outputs, links, reflections | null |

**Every field is always present in the YAML block**, even if its value is `null`. The schema is rigid; the values are flexible.

## Extraction rules (deterministic)

When the user pastes prose, follow these rules **strictly**. This is the heart of the skill — violating it produces noise that propagates through all aggregations.

### Rule 1 — Item detection

A **task boundary** is any of:

- A line starting with `-` or `*` or `•` (optional indent).
- A line starting with a number followed by `.`, `)`, or `:` (e.g. `1.`, `2)`, `3:`).
- An explicit separator line the user writes (blank line between paragraphs counts only if there are no bullets at all).

If the input has **zero enumerated items**, treat the whole input as **one task**.

If the input has **at least one enumerated item**, only enumerated items become tasks. Prose before/between bullets is context for the nearest following bullet (goes into `body` of the next task).

**Never merge two bullets into one task. Never split one bullet into two tasks.** The count must match exactly.

**Implicit paragraph boundaries (unbulleted batches).** When the user pastes a large batch of to-dos without bullets but each starts a new paragraph (blank line between them, or each begins a new line with a capitalised action verb like `Escribir`, `Meter`, `Entender`, `Revisar`, `Crear`, `Añadir`, `Hacer`, `Corregir`), treat each paragraph as one task. The action-verb-at-line-start heuristic is the primary signal; the blank-line heuristic is the fallback.

**Embedded fenced / quoted content is NOT a task separator.** A `\begin{enumerate}…\end{enumerate}` inside a task's prose does not split it into 9 sub-tasks. A pasted ChatGPT answer inside a task's prose does not split it. A pasted Twitter thread, a code block, a URL list, an LLM transcript — none of these are task boundaries. They are body material belonging to the enclosing task. When unsure whether something is a new task or embedded content, ask: does it start with an action verb addressed to Omar (new task) or is it quoted/pasted material relevant to the previous task (body)?

### Rule 2 — Per-item field extraction

Scan each item for these tokens. Each token is recognised regardless of position. Remove token from the title after extracting.

| Token pattern | Field | Example |
|---------------|-------|---------|
| `P0` / `P1` / `P2` / `P3` (standalone, uppercase) | `priority` | `P0 llamar juan` → priority=P0 |
| `#<slug>` | append to `tags` | `#matematicas` |
| `@<slug>` | `project` (first one wins) | `@reflexiones_a_latex` |
| `YYYY-MM-DD` | `when` | `2026-04-25` |
| `hoy` / `today` | `when` = today's date | |
| `mañana` / `tomorrow` | `when` = today + 1d | |
| `lunes`/`martes`/`miércoles`/`jueves`/`viernes`/`sábado`/`domingo` or English weekday | `when` = next occurrence of that weekday | |
| `mañana` (lowercase, standalone after a time context) | `time_of_day` = morning | only if clearly "in the morning", not if it's "tomorrow" |
| `por la mañana` / `in the morning` / `AM` | `time_of_day` = morning | |
| `por la tarde` / `afternoon` / `PM` | `time_of_day` = afternoon | |
| `por la noche` / `evening` / `night` | `time_of_day` = evening / night | |
| `<N>h` / `<N> horas` | `duration_min` = N*60 | `2h` |
| `<N>m` / `<N> min` | `duration_min` = N | `30m` |
| `HH:MM` | `time_of_day` inferred (< 12:00 morning, 12–18 afternoon, 18–21 evening, >21 night) AND add to body | |
| `low-energy` / `poca energía` | `energy` = low | |
| `high-energy` / `mucha energía` | `energy` = high | |
| `@home` / `@office` / `@outside` / `en casa` / `en la oficina` | `location` | |

Ambiguity resolution: if a token could be either `when=mañana (tomorrow)` or `time_of_day=morning`, prefer `when=tomorrow` when it appears as a standalone word, prefer `time_of_day=morning` when it follows a time preposition (`por la mañana`, `in the morning`).

### Rule 3 — Title cleanup

After extracting tokens and bodies (Rule 4), the `title` is the **opening imperative only** — the first sentence / first clause of the task, up to the first period or natural stop. Trim whitespace, collapse multiple spaces, strip leading punctuation (`-`, `*`, `•`, `1.`). Do **not** rewrite the phrasing. Do **not** translate. Keep Omar's words as-is. If the opening imperative exceeds ~120 characters, that's fine — keep it; the title can be long if Omar wrote it long. Do not invent a shorter title.

### Rule 4 — Body as verbatim archive (non-negotiable)

**The body is a faithful archive, not a summary.** When the user's task prompt contains material beyond the opening imperative — embedded LaTeX, pasted ChatGPT/GPT output, Twitter/X threads, code snippets, long multi-paragraph reflections, mathematical derivations, reference lists, URL dumps — all of it lands in `body` **verbatim**. Not summarised. Not paraphrased. Not truncated. Not translated. Not reformatted (beyond trimming the leading bullet/indent on the first line). Not "cleaned up".

**Why.** The ledger doubles as Omar's long-term research notebook. He often thinks through a problem in the act of writing the task — pasting a ChatGPT explanation, dropping a LaTeX derivation, quoting a Twitter thread he wants to preserve. If the skill compresses that to a one-line summary, the thinking is gone and the task is useless as an archive. Six months later Omar wants to open the task and find **exactly what he typed** — not a compressed gloss.

**Rule of thumb.**
- If the task text is exactly one sentence → title = that sentence, body = `null`.
- If the task text is more than one sentence → title = the opening imperative (first clause, per Rule 3), body = **the entire original task text, verbatim, including the title sentence itself**. The title is a derived index into the body; the body is the ground truth. Never drop content from the body because it "looks like boilerplate", "is just LaTeX", or "is a ChatGPT dump the user probably doesn't need". Keep it all.

**Concrete examples.**

**Example A — embedded LaTeX block.**

User writes:

> Explicar el concepto de representación de mundo en mates financieras mediante espacio de probabilidad.  In order to organise ideas, it is convenient to begin with a purely discrete model [...continues with \begin{enumerate}...\end{enumerate} spanning several pages of LaTeX...]

→ `title`: `"Explicar el concepto de representación de mundo en mates financieras mediante espacio de probabilidad"`
→ `body`: **the full original paragraph including the entire LaTeX source**, preserved character-for-character. All `\begin{enumerate}`, `\item`, `\[...\]`, `\mathbb{...}`, etc. stay intact. No section is dropped because "it looks like boilerplate".

**Example B — embedded ChatGPT output.**

User writes:

> UTILIZAR EL TEXTO DE CHATGPT. meter en los apuntes de generales un ejemplo en mecánica teórica en el cual vamos a trabajar con un sistema simple [...long ChatGPT explanation about polea, Hamiltonian, constraints...]

→ `title`: `"UTILIZAR EL TEXTO DE CHATGPT. meter en los apuntes de generales un ejemplo en mecánica teórica"`
→ `body`: the complete ChatGPT dump verbatim — the whole polea mechanics narrative, Hamiltonian construction, ligadura derivations, all of it.

**Example C — embedded social-media thread.**

User writes:

> Escribir qué Hay un resultado simplemente espectacular en teoría de derivados [...pasted thread from Volatility's fray with tweet timestamps, usernames, view counts, UTF-8 glyphs, OCR artefacts...]

→ `title`: `"Escribir qué Hay un resultado simplemente espectacular en teoría de derivados"`
→ `body`: the full thread as pasted, including the timestamp "21:12 • 28/10/24", the view counts, the Japanese glyphs and OCR noise. Do not try to "clean it up" or drop the noisy OCR characters.

**References marker.** If a continuation block is introduced explicitly by `refs:`, `chatgpt:`, `gpt:`, or `ref:`, route THAT specific block to `references` instead of `body`. Everything else (including ChatGPT output that ISN'T explicitly marked with `chatgpt:`) stays in `body`. If a task has both a long body and a marked references section, split them accordingly — both stay verbatim.

**Bullet continuations.** If the user's bullet spans multiple lines with indented continuation, all continuation text joins `body` verbatim (same rule: preserve, don't compress):

```
- estudiar banach 2h #matematicas
    necesito terminar capítulo 3 antes del miércoles
    chatgpt dijo que empezara por el teorema de hahn-banach
```

→ `body`: `"necesito terminar capítulo 3 antes del miércoles\nchatgpt dijo que empezara por el teorema de hahn-banach"` (both continuation lines, verbatim).

**Empty body is the exception, not the default.** Only set `body: null` when the user genuinely wrote only one imperative sentence with no additional context. When in doubt, err on the side of including the full text in body.

### Rule 5 — Routing by `when`

A task's `when` field determines which Daily file it goes into:

- `when` is a date → file = `Ledger/Daily/<when>.md`
- `when` is null → file = `Ledger/Daily/<today>.md` (today is the fallback logging bucket)

Never split one task across two files.

### Rule 6 — Never invent (except tags, which are a deterministic function of content)

If a field is not explicitly signalled by the user's text, it stays **null**. This includes priority, project, duration, date. `P2 as default` is NOT an invariant — leave it null.

**Tags are the single exception.** Rather than leave tags empty, we run a deterministic classifier (`classify_tags.py`) against the task's full text (title + body + references + project slug) and emit every tag whose regex matches. User-provided `#tag` tokens are always preserved and unioned on top. The classifier is a pure function — same inputs always give the same sorted output, no randomness, no clock, no remote calls. Details in the "Tag auto-classification" section below.

The auto-stamped fields on creation:

- `id` — deterministic from date + correlative.
- `created_at` — now.
- `status` — `open` on creation.
- `tags` — union of user-provided tags + auto-classifier output + parent-chain closure.

## Procedure

### On log request (the common case)

1. **Scope**: verify the requested operation and exact authorized paths in the current assignment.
2. **Parse prose**: apply Rules 1–6 to produce a list of task dicts (Python-serializable JSON).
3. **Call `log_task.py`**:

   ```bash
   echo '<json-array>' | python3 scripts/log_task.py
   ```

   Script assigns IDs, creates Daily files as needed, appends blocks in enumerated order, writes frontmatter, stamps `created_at`.
4. **Call `aggregate.py`**: regenerate Weekly/Monthly/Yearly + `_index.json` for the affected week/month/year.
5. **Return payload**:

   ```
   action: log
   tasks_created: N
   files_touched: [paths]
   weekly: <path>
   monthly: <path>
   ```

### On update request (close / cancel / block / roll over / edit)

1. Resolve task by `id` or by title fuzzy match within a date range (ask if ambiguous).
2. `python3 scripts/update_task.py --id <id> --set status=done [--body "..."]`.
3. Re-run `aggregate.py`.

### On query request

1. `python3 scripts/query_tasks.py --tag <x> --status open --since 2026-04-01 ...`.
2. Return formatted table or JSON per caller.

### On report request

Rollups are already materialized in Weekly/Monthly/Yearly. For custom rollups (tag-specific, date range, cross-project), `query_tasks.py` with filters is sufficient. Point user to the generated file when a standard view covers their ask.

## Generated views

### Weekly (`Weekly/YYYY-Www.md`)

Contains, in order:

1. **Stats header** — total logged, done, open, cancelled, rolled_over, completion %.
2. **Per-day table** — Mon…Sun × (count, done, top priority).
3. **Full task table** — every task that week, columns: date, time, title, priority, status, project, tags, duration.
4. **By priority** — P0/P1/P2/P3 buckets.
5. **By project** — task count + completion % per project.
6. **By tag** — top N tags with counts.
7. **Overdue** — open tasks whose `when` is before week end.
8. **Rolled-over** — tasks with status=rolled_over.

### Monthly (`Monthly/YYYY-MM.md`)

Same sections but aggregated per-week instead of per-day.

### Yearly (`Yearly/YYYY.md`)

Per-month aggregation + top tags/projects/priorities of the year.

### `_index.json`

Flat array of every task in the ledger. Shape: `[{id, title, when, status, priority, project, tags, …}, …]`. This is the query backbone — fast, deterministic, trivially parseable by any other agent, dashboard, or analysis script.

## Tag auto-classification

Tags are not user input; they are a **deterministic function of the task's content**.

### Mechanics

1. After `log_task.py` or `update_task.py` normalises a task, it calls `classify_tags.classify(title, body, references, project, existing_tags)`.
2. The classifier loads `tag_taxonomy.yaml` (~90 entries today, grows over time). Each entry has: `name`, optional `parent`, a list of regex `patterns`. Patterns are case-insensitive, word-boundary Spanish+English.
3. For each tag, if **any** of its patterns matches the concatenated text, the tag fires. Parent tags fire transitively (if `analisis_funcional` fires, `mates` fires too).
4. User-provided `#tag` tokens from the original prose are never dropped — they are passed in as `existing_tags` and the final set is the **union**.
5. If a task carries `project: scilux`, a synthetic `proyecto_scilux` tag is auto-added regardless of whether the taxonomy caught it.

### Invariants

- **Pure function**. `classify(X) == classify(X)` always. No randomness, no clock, no network.
- **Additive**. Auto-tags are always **added**. A user tag is never removed by the classifier — the worst case is that the taxonomy simply doesn't recognise it and it survives unchanged.
- **Parent closure**. Querying `--tag mates` returns every math task; `--tag analisis_funcional` returns the FA subset. Hierarchy is expressed by `parent:` in the YAML.
- **Editable without code**. Adding a new tag = adding an entry in `tag_taxonomy.yaml`. No Python change required. The classifier caches at import time; new tags take effect on next process.

### Reclassify existing tasks

When the taxonomy is extended, `reclassify.py` re-runs the classifier against every task in the ledger, rewrites the affected Daily blocks in place (preserving body/references verbatim), and re-runs `aggregate.py`. User tags are carried through untouched.

```
uv run /Users/omarkhalil/GitHub/Constellation/skills/omaros/task-marshal/scripts/reclassify.py              # all days
uv run /Users/omarkhalil/GitHub/Constellation/skills/omaros/task-marshal/scripts/reclassify.py --only 2025-01-15
uv run /Users/omarkhalil/GitHub/Constellation/skills/omaros/task-marshal/scripts/reclassify.py --dry-run    # no writes
```

### Tag reports

`tag_report.py` walks `_index.json`, filters by one or more tags (AND-combined), and writes a standalone markdown dossier under `11_Documents_and_Reports/Task_Tag_Reports/<slug>.md`:

```
uv run /Users/omarkhalil/GitHub/Constellation/skills/omaros/task-marshal/scripts/tag_report.py --tag finanzas
uv run /Users/omarkhalil/GitHub/Constellation/skills/omaros/task-marshal/scripts/tag_report.py --tag mates --tag estocastica --title "Mates+estocástica"
uv run /Users/omarkhalil/GitHub/Constellation/skills/omaros/task-marshal/scripts/tag_report.py --list      # tag inventory with counts
```

The report contains: overview stats, status/priority/project/month breakdowns, co-occurring tags (how the queried tag overlaps with the rest of the taxonomy in practice), and the full task list grouped by status with every body and references block inlined, so the report stands on its own without needing to open the Daily file.

## Scripts

- `scripts/parse.py` — shared library. Reads any Daily/*.md, yields list of task dicts. Robust to whitespace, handles `\`\`\`yaml task` fenced blocks.
- `scripts/classify_tags.py` — loads `tag_taxonomy.yaml`, returns deterministic tag list for a task.
- `scripts/log_task.py` — appends new task blocks to Daily files from a JSON array on stdin; auto-classifies tags.
- `scripts/update_task.py` — mutates a task by id (status, priority, body, tags, …); re-classifies when title/body/refs/project change.
- `scripts/reclassify.py` — walks every Daily file, re-runs classifier, rewrites blocks in place.
- `scripts/aggregate.py` — regenerates Weekly/Monthly/Yearly + `_index.json` + `_by_tag.json`.
- `scripts/query_tasks.py` — CLI filter over `_index.json`, prints markdown table or JSON.
- `scripts/tag_report.py` — per-tag deep-dive reports under `11_Documents_and_Reports/Task_Tag_Reports/`.

All scripts are idempotent; re-running `aggregate.py` on unchanged input produces byte-identical output (stable sort keys).

## Constraints (hard)

- **CRITICAL**: every enumerated bullet ↔ exactly one task. Count must match.
- **CRITICAL**: missing fields = `null`, never invented defaults (except `status=open`, `tags=[]`, auto-stamped `id`/`created_at`).
- **CRITICAL**: the `body` field is a VERBATIM archive of everything the user included beyond the opening imperative. Never summarise, paraphrase, compress, translate, truncate, or "clean up". LaTeX sources, ChatGPT pastes, Twitter threads, code snippets, multi-paragraph reflections, URL lists — all preserved character-for-character. See Rule 4. If in doubt, keep more, not less.
- **CRITICAL**: Weekly/Monthly/Yearly are **generated**. Never edit by hand. Never commit a hand-edited weekly view.
- **CRITICAL**: once a task has an `id`, that id is immutable. Transitions mutate status/closed_at, never the id.
- **CRITICAL**: on `status → done` or `cancelled`, stamp `closed_at` to the current ISO timestamp.
- **CRITICAL**: `blocked` and `waiting` tasks must carry a `body` explaining the blocker/party.
- **CRITICAL**: never delete. A cancelled task stays in its Daily file with `status: cancelled`.
