# Ecosystem evaluation

## What is evaluated

Evaluation relates each requirement to a controlled input, expected behaviour
and an independent observation. It distinguishes three objects: the engine that
validates contracts, the integration that runs events in a particular client,
and the agent that decides which capabilities to use and produces the outcome.
Success in one does not certify the others. Counts of tests, roles or skills
are not a measure of semantic reliability.

The case set must include simple tasks, justified combinations of capabilities,
unavailable tools and failures. For selection, sets of required, optional and
forbidden capabilities are declared; a proposed alternative is recorded
separately from what was actually selected and executed. Variants must change
the conceptual need, rather than just keywords. A positive case needs a negative
control that reveals unnecessary activation, acceptance of missing evidence or
an unchecked dependency.

Evidence distinguishes the exposed catalogue, consulted instructions, tool or
agent executed and checked artifact. Incomplete outcomes and rejections retain
their status; a later success does not erase a failed attempt. A catalogue or
the agent's own declaration is insufficient to certify use. Observation
publishes only curated operational evidence, without prompts, transcripts,
credentials or private data.

This matrix specifies the candidate's obligations; its presence does not mean
that trials have finished. [Observed compatibility](compatibility.md) records
the delivery's execution status and limitations.

| Obligation | Required evidence | Rejection to check |
| --- | --- | --- |

| Complete bundle and partial modules | Reproducible build, exact inventory and tests from the package without the source checkout. | Missing, extra, altered or linked resource, or unavailable module. |
| Update 1.3.0 → 1.3.1 | Both installers verify the old and new versions separately, preserving data and settings. | Mixed inventory, someone else's change and failure during replacement, with tested recovery. |
| Codex and Claude integration | Identified client and version; catalogue, trust and events actually observed are recorded separately. | Unknown state is not turned into permission or success. |
| Scope and closure | Allowed edit within the plan, denial outside scope and a pending contract that remains incomplete. | Missing/failed evidence, incorrect identity or stale closure. |
| Subagents | Native launch, identity, outcome and applicable events observed in the tested client. | Missing outcome, failure or approval rejection without attributing executed work. |
| Static guidance without a contract | Native context receives the same reminder without reading prompt/transcript or creating task state. | Implicit contract creation, classification of private content or added permission. |
| Capability selection | Scoped cases with need, choice, instructions read and outcome checked, including diagnosis without edits and nontrivial arguments. | Selection by an irrelevant word, missing capability presented as used or delegation without benefit. |
| Review and publication | Actual authors, current independent coverage and remote SHA verified by Git owner. | Self-review, open finding, subsequent change or different destination. |

Installation can be tested without model calls. Semantic evaluation requires
actual agents and its own criteria for sources, arguments and quality; a
simulated HTTP response does not replace that trial. Comparisons between clients
or configurations fix cases, versions, budget, attempts and metrics before
interpreting outcomes. More delegation can increase cost and latency: an
improvement is not inferred from the number of agents. A static reminder may
guide selection, but its presence and privacy tests do not prove that a model
follows it. A guidance change requires new actual cases; a small sample does not
establish a universal guarantee or causation.

complete reevaluation after the subsequent delta. Each repair requires
independent verification; that judgement does not replace formal resolution of
the finding against the token containing the final reviewed version. New or
pending findings retain their status. Publication belongs to the workflow.

The final probe correction rejects every tool outside an explicit allowlist
and passed five focused tests. The five native cases with simulated responses
document the earlier trial; they are not confused with validation of that delta.
Their policies separate the trusted Claude binary — HOME, Keychain and external
network denied; temporary writes — from the candidate CLI, which adds a clean
environment, fixed cwd and strict reads. The test records each boundary; it does
not generalise the strictest boundary to every process or interpret a simulated
response as a model evaluation.

expected bytes, and the undeclared write was denied without creating the file.
Operations retained the parent session; start and finish events and the agent's
final state were observed. The contract remained `active`, as appropriate for its

does not test Git publication, autonomous delegation or closure.

## Reproducible checks

From the source checkout, the suites use temporary repositories, remotes and
homes. The coordinator records appropriate commands in its workflow:

```sh
python3 -B .codex/ecosystem/validate.py --root .codex
python3 -B -m unittest discover -s .codex/tests -q
python3 -B -m unittest discover -s .codex/ecosystem/tests -q
```

The distribution is also checked from its own directory, without retrieving hub
sources. Native diagnostics and model trials are recorded separately: they are
not inferred from these suites' output. Changing code, content, scope or policy
requires the affected evidence to be renewed before publication.

The evaluation design follows the distinction between tools, handoffs and
outcome in [OpenAI Agent evals](https://developers.openai.com/api/docs/guides/agent-evals),
and the positive and negative cases and controlled environments described in
[Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents).
These are public criteria for designing trials, rather than certifications of
the package.

## Historical record

JSON results are retained in full, only in the sources, in
`ecosystem/evals/results/2026-10-18.json`. The report
`ecosystem/docs/history/constellation-1.1.md` brings together earlier evaluations;
`ecosystem/docs/history/omaros-1.2.md` retains the runtime delivery to the receiver.
Their paths, metrics and versions describe those trials, rather than the current
tree. They are not distributed as runtime dependencies or substitutes for the
1.3.1 tests.

The adaptive harness and its local work report were excluded from the previous
delivery because they belonged to an independent evaluation awaiting publication.
This reorganisation neither adopts nor deletes them, nor turns them into an
executed series.
